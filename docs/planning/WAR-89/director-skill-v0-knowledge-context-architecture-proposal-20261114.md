## 1. 为何不是整段上下文持续对话，亦不是多 Agent 默认分工

| 方案 | 优点 | 实际代价与主要失败模式 | 本轮判断 |
| --- | --- | --- | --- |
| A：单 Agent 连续聊天 | 简单、临时试探顺畅、无打包开销 | 长会话埋掉早期承诺；难恢复、难隔离版本、局部修订可能污染全局；上下文占用大 | 适合单阶段探索，不作可恢复项目的权威状态 |
| B：统一 Skill + 独立阶段调用 | 阶段能重试/换模型/局部修订；状态与证据明确；小上下文可控 | 需要可靠的上游摘要、决策理由与引用；漏包会使摄影变成无动机参数优化 | **默认方向**，加入“Scene Spine + 当前决策包 + 依赖查询” |
| C：多专业 Agent 协作 | 异质专业并行审核、隔离竞争性方案 | 多轮消息、协调争议、成本和责任漂移；多个 Agent 容易各改作者约束 | 默认不采用；只在复杂冲突或独立反例价值明显时启用短时审阅 |

**协调角色**：轻量 Stage Orchestrator 选择目标阶段、正式快照、专业知识包、必要的上下游引用与恢复路径；可以在早期手工组装，不假设现有 Engine/API 已可生产使用。**导演责任**：统一 Director Skill 需依据已批准 Scene 意图产生专业选择并解释取舍；模型没有独立拥有已确认故事事实的权力。**状态/权限责任**：工程服务保管已批准版本和验证结果，人工确认仍在 WAR-74 默认审阅 A（Intent）/B（Plan/Review），遇硬冲突提前介入。

## 2. 五层上下文而非七个常驻专业模块

| 层 | 放什么 | 生命周期与加载规则 |
| --- | --- | --- |
| L0 Skill 常驻不变量 | 已确认故事优先、从观众任务推导选择、Beat≠Shot≠执行单元、信息与动作时序不能偷改、已批准与候选/未证分清、关键决定留可追溯理由、遇实质冲突才上游申请 | 每个专业调用都带**短原则**；不加载全部 K1–K7 正文 |
| L1 阶段任务卡 | 此阶段要回答的专业问题、最小输入输出、典型失败信号、默认审阅门槛 | 只加载目标阶段一张短卡；与 L0 共同构成模型工作说明 |
| L2 问题触发专项 Reference | 按 K1–K7 路由的 DS/TF/VM 有关小节、具体正反例与停止条件 | 检出具体风险或确有选择分歧才读；一次先用主来源，必要才补第二来源 |
| L3 当前项目正式依据 | 来源剧本/作者约束、批准 Intent、Beat/Blocking/Shot 相关语义、原因/被排除方案、变更及未证风险、当前周边状态 | 每次根据**批准快照**构造；不是全量历史对话，也不是从上次回答猜事实 |
| L4 工程与媒体证据 | schema/引用/版本/依赖/一致性检查结果、现有参考覆盖、真实/代理媒体证据边界 | 工程程序计算和提供**可理解摘要**；需要时带精确链接；不把 JCS/SHA 等实现细节常驻给导演 |

建议 L0 为**一小段不超过一屏**的原则，不强制七类问题逐镜打勾。L3 的“Scene Spine”（下文）每次阶段调用保持，L2 只选择少量相关专业文档。知识索引记录来源标识、相对文件、标题/行段、适用与不适用条件、许可证状态；未来实现需核对目标路径可读、版本匹配，取不到来源时应显式降级而非凭记忆伪装已查阅。

### L0 最小专业原则（候选可执行措辞，不是现在要写入 Skill 的文件）

1. 把作者确认事实/禁项与导演可选择的表达手段分开；不得自行把解释变为源事实，重要修改必须走原批准关口。
2. 对每项重要导演选择先交代**观众要得到/暂不得到的信息或体验**，再谈 Blocking 或摄影；整场政策和 Beat 变化是两件事。
3. 确认行为、听觉/视觉因果、人物与观众知情的时间顺序；动作可跨切，镜尾可在进行中。
4. 关键镜头说明可辨的画面/声音机会；“物体露出”“模型声称可见”“参考文本 fully covers”都不是已通过媒体证明。
5. 有真实取舍才比较少量替代拍法；不得用固定镜头数、焦距、Beat 数或 H3 执行长度反推剧情结构。
6. 区分已批准、候选、确定性冲突、专业上可争议的方案、未证物理/媒体风险；局部修订需反查必要下游与整场交付。

加载算法（概念，不预定工具 API）：
1. 从任务卡与 L3 当前决策包识别**已出现**的专业问题；先带 L0 + 所在阶段最小方法。
2. 若通用知识足以做出有创作理由的决定，则**不读**其他来源；若存在触发标志，按上表选一个最相关的小节。来源不设绝对优先级，问题可由 TF 或 VM 主导。
3. 只在主来源不能解释真实争议/有相互冲突的方法时读第二来源，再按作者事实优先与当前导演目标裁决。
4. 专业决定已能说明“为什么这样拍/为什么不选另一法/哪项未证”即停止；**不因还有未加载文档而继续加载**。证据缺失可标未知，不允许伪称已经核验。
5. 发生新反馈、版本变化或上游意义变化，才重新路由受影响知识；相同场景、相同来源版本可复用提取的索引，但**不能把缓存的专业判断当成批准的创作事实**。

## 4. 分阶段上下文契约：每次独立调用最少需要什么

### 4.1 全部阶段共用的 Scene Spine（短、稳定、版本明确）

Scene Spine 不是第五种正式 DirectorPlan 产物，而是**从已批准正式状态临时汇编的调用视图**：
- 场景身份、Story Basis 当前来源版本与可靠引用；不可违反的剧情行为、台词/文字、知情/声画顺序及用户禁项（给关键原文定位）。
- 已批准 Director Intent 的**观众目标与整场导演政策**，包括“为何选这一路线、拒绝过哪些足以影响下游的方向、什么能局部例外”；尚未批准时明确 draft。
- 完整场景的**Beat 弧线简述和交付责任概览**（哪段负责观众首次见到什么、后续重新认识什么、结尾交付什么），避免局部镜头好看却丢失全场目标。
- 对当前调用 relevant 的已批准版本、用户确认/禁止项、未证风险；必要引用用于正式回读，不能用指纹替代语义。

Scene Spine 可压缩无争点细节，但**不能丢失会改变下游选择的禁项和原由**；保持不代表一次模型直接看到长剧本全部字节。如果任务是首次全场覆盖/精确对白、文字、源冲突审核，需回读原始对应段落。

### 4.2 各阶段必要输入、可以压缩的与必须精确保真的

| 当前调用 | 必需直接提供 | 可按摘要提供；何时回看原文 | 产出要留下的专业依据 |
| --- | --- | --- | --- |
| Director Intent | Story Basis 中场景核心事件、作者已确认意图/禁项、原话和关键知情时序；当前候选/批准状态 | 全场剧本可用紧凑摘要导入，但关键原话与反常行为须精确引用；有争议回看原文 | 观众目标、整场政策、为何这样表达、自由度/禁项、真实替代及取舍 |
| Beat | 批准 Intent、全场不变量、原事件/对白的顺序和终局、观众与人物信息变化 | 音色/机位等暂不需要；普通动作可概括，决定性沉默/台词/文字必须按原序 | 每个变化的起因和起/终认知状态、对应观众压力、重要停顿与连续时间关系 |
| Blocking | 批准 Intent 摘要、相关 Beat 的完整行为与时序语义、世界空间/道具已确认关系 | 不相关 Beat 只需场景弧线；关键交接/遮挡/眼线从剧本和 Beat 回读原段落 | 表演动机、关键中间态、身体/视线假设、替代行动、哪类未证几何会影响镜头 |
| Shot Plan | **Scene Spine + 所选 Beat 的完整信息任务与严格顺序 + 完整有关 Blocking（含中间态） + 相邻镜/全场覆盖摘要 + 已知参考缺口与批准/候选状态** | 其他 Beat 简述并保留索引；已有审阅历史只留影响决定的理由；关键对白/背字/声源和硬约束需精确引用 | 每镜观众任务、构图/机位/运动/时间/切点的理由、同镜/插镜/反应镜可行取舍、可信证据窗口与未证项 |
| Review 横切 | 被审对象、Story Basis/批准 Intent 的不可变要求、变更 diff、直接/间接依赖与验证级别 | 局部审阅只取有关镜/邻镜，但带 Scene Spine；整场 B 审阅必须从**原剧本正向查交付位置**并从镜头反查源依据 | 分开“硬错误／合理争议／规划风险／未证媒体”，定位根因、修订及复检覆盖 |

**保真规则**：源对白、照片上的准确文字、已确认动作/知情时点、禁止改变的故事因果，不能以模糊摘要替代；必要时给来源定位并提供原文片段。镜头数、焦距、未选方案的全部草稿推理、格式验证器日志等可删减；只保留会导致不同摄影/表演判断的上游取舍依据。保存的是**可检验的决策说明**（依据→理由→预期观众效果→已拒方案与代价），**不是历史完整对话或模型内部推理**。

### 4.3 Shot Plan 的最小充分上下文：为什么 Blocking 单独不够

一次针对整场 Shot Plan 的调用，建议至少得到六组信息：
1. **全场 Scene Spine**：观众的认知策略、预期情感、整场视听政策、不得违背的已确认剧本限制；优先级最高。
2. **当前 Beat 的信息时间线**：谁在世界中知道/看到/听到什么、观众何时首次获得证据、关键中间态和压力变化；不止 Beat ID。
3. **有关 Blocking 的动作时间线**：人物与道具初态、动作/眼线/遮挡的关键时刻、未完成动作边界、已批准 vs 假设；不止站位图。
4. **相邻镜与全场覆盖**：哪些观众任务已交付或待交付、邻镜状态/声画切点、整体节奏和可用时长；减少局部最优而漏结尾。
5. **来源证据和制作现实**：必要剧情/对白/文字原文及定位，现有参考实际支持什么、缺哪些新视面；不虚构已制作素材。
6. **决策沿革摘要**：**为何**批准当前 Intent/Blocking、否决过什么会改变摄影取舍的方案、当前局部用户意见及未证风险；不载入所有曾经尝试过的方案。

**整场 Shot Plan 初次设计**：保留全 Beat 弧线，依镜头覆盖的局部提供详细 Beat+Blocking，必要时分批迭代再进行全场校验。**单 Shot 局部修订**：同一 Scene Spine + 被改镜/邻镜 + 相关 Beat/Blocking + 会受影响的全场覆盖摘要，不必加载全部镜头详稿。这个规则是“最小充分语义”，不是现在要冻结的固定 JSON/tokens 配额。

## 5. D《错过的钥匙》——一次 Shot Plan 调用示例（说明性模拟，未运行）

### 5.1 从上游传入的 Scene Spine 与局部包

**Story Basis 不变量（冻结剧本）**：办公室长桌、门、文件、蓝色文件夹、**唯一**银色钥匙；观众先于林看见第一次露出的钥匙；林无意再次遮住；周仅看到文件夹遮桌的位置并推断异常，不是目击钥匙；林**第二次**移开蓝夹后看到钥匙并有短暂停顿；周伸**右手**，林把钥匙交到她右手；周持钥匙离开，林留在桌边。整体自然，不夸张喜剧。来源指向上述 D 冻结原文行；不从模型的摄影建议重写该事实。

**已批准 Intent（用于本例的语义假设，不声称源文件里已有实际批准记录）**：注意力错位：让观众在林的无意遮挡后先感到“答案刚被挡回去”，而周仍只因文件夹位置异常发问；表演克制，摄影不把周误拍成先看见钥匙。决策理由：观众与人物的认知落差比追求炫技切镜重要。

**相关 Beat（演示性转换，非原冻结 Beat ID）**：
- B2：文件移开，唯一钥匙第一次露出；观众获得可信识别机会，林未察觉。
- B3：林拿蓝夹再次挡住，周走到桌边、看到遮位并发问；她尚未目击钥匙。
- B4 交接前的下游提示：林再次移开蓝夹，看见钥匙并尴尬停顿；避免把“第一次未察觉”错误延伸至第二次。
全场摘要还须保留 B4 后唯一一次交接和离开，以免局部拍法预支后续状态。

**有关 Blocking（例示输入）**：林移文件→钥匙出现于桌面→林注意在整理任务而非钥匙→林抬起蓝夹重新盖住钥匙；周从门侧接近，眼线指向蓝夹遮桌处，未直接得到钥匙视觉证据。世界位置与画面左右区分，遮挡/眼线的真实几何未证。局部空间事实以已批准北墙长桌、东墙门的版本为准；本例不重新批准具体几何。

**已有摄影/制作证据**：WAR-74 记录的 WAR-72 代理画面中，原 Shot02 40mm MS/6s 的钥匙约 27×9px 且部分遮挡，**不能由此认定观众已发现**；也不能推出 40mm 一定失败。当前 D 原剧本声明尚无真实图像资产；不可伪称已经拥有可用于镜头的新参考图。

### 5.2 只加载哪些专业知识

- **通用** L0 + Shot Plan 阶段任务卡，以及 K1/K2 已确认知情不变量；不回读全部 K1/K2 原始长文。
- **DS cinematic-language** 的“镜头观众任务、景别/构图/同镜与切镜的有理由选择”相关小节（K5）；需要时补 TF shotCraft 的“观众信息/反应先后”段。
- **VM storyboard_artist** 的关键中间显露/再遮及镜头前后状态可解释性（K4/K6）；如果拟选的客观特写引入现有参考未覆盖的表面，才补 VM camera_image_generator 的 missing_info 思路（K5）。
- **不加载** TF 全类型库、DS 20 个风格模块、VM Python Pipeline/Camera Tree、完整 E/C 测试、H3 参考扩张机制、全量历史聊天、WAR-35 JCS 校验细节。无文本读字/画外声争议，不触发 E/C 对应专题。

### 5.3 期望模型真正做出的摄影取舍

**候选 A：维持关系镜**。镜头包含林移文件、钥匙露出、林注意转移及蓝夹遮回，周进入时眼线保持指向蓝夹覆盖区。优点：保留林无意动作与关系表演的连续性；失败风险：钥匙在画面小或短暂时，观众可能根本没看到。必须设计**可信的露出窗口与注意引导**，不能只写“钥匙可见”。

**候选 B：客观钥匙插镜**。在第一次露出时给观众明确证据，再回到人物/蓝夹遮挡。优点：信息可辨性更容易规划；代价：容易显得刻意，且若机位/反应连接暗示“周的 POV”，会错误改变周的知情来源。插镜应明确为客观观众信息，而非周目击；仍需核叙事节奏和可用参考覆盖。

**决策建议**：先保留 A 与 B 为确有差异的候选；由于 WAR-72 已揭示 A 的既有代理构图未能证明可读，不能重复宣布 A 合格。可优先比较改机位/主体比例/焦点的 A' 与客观插镜 B 的可辨性成本，选定后记录“为何保住观众先见且不误导周的知情”，以及媒体/几何待证。不要凭尚无的真实媒体强断 B 必胜。

**反面样例**：只给 “Shot02 40mm；Shot03 85mm ECU；镜头有电影感”，不交代钥匙在**哪个中间时刻**对观众可信可辨、周为何不应读到钥匙、镜头为何切换、是否错改第二次林发现，即为“专业知识术语复述而未参与决策”。

## 6. 编排、重试、人工修改与审阅责任

**Stage Orchestrator（轻量）**执行：选择已批准 Scene/版本→确认目标阶段和工作范围→生成 Scene Spine→收集当前相关上游与变更摘要→识别专业触发→选择必要 Reference 小节→调用 Director Skill→呈现候选/提交→由工程适用时校验、持久化和返回精简错误→交用户 A/B 或风险型审阅。此为**未来最小接口职责**，不是已经存在的工具。

- **阶段重试/模型切换**：重新从相同正式快照构建上下文；候选尝试不污染批准版本，比较真实变动/理由。不同模型/思考强度允许：简单确认/出处整理由低成本模型；Intent/Beat/Shot 复杂取舍使用较强推理；高争议、硬约束近失误、媒体假设冲突时采用独立审阅，不是每阶段固定 Astra。
- **局部用户编辑**：首先判定编辑目标是 Shot 摄影、Blocking 行为、Beat 时点还是 Intent/Story Basis 方向；若改摄影却隐含改变周知情，应退回上层授权。仅重新运行必要阶段并复核所有**受影响**后继、邻镜与全场相关覆盖，不因一个镜头变化全部推倒，也不能跳过信息时点跨段影响。
- **Review 责任**：Creator 可以自检但不自证媒体通过。独立 Reviewer 可在高风险、创作争议或方案明显自相矛盾时作为短时调用，仅返回可定位反例和证据等级，用户对已批准表达方向保有最终裁决；硬源冲突不能用“接受开放风险”豁免。
- **人工/Canvas 接续**：未来 Canvas 只须把编辑的目标、批准的旧版、候选修改、受影响引用、用户意见、媒体证据等级写入正式状态；再次调用重建相应包，不靠 Canvas 留存一段无限增长的聊天。
- **最小提交/错误反馈**：先创作自由草案，再输出足以映射 WAR-35/52 的正式语义提交；若工程检查失败返回“具体镜头/状态与哪项已批准约束冲突，允许如何修”，不把 hash/JCS/CheckSpec 内部细节泄露为导演推理要求。此处**只提出需求**，接口归属/生产 Engine 需后继任务批准。

## 7. 最小专业反馈格式与三份冻结案例验收设计

一次有实质摄影/Blocking 取舍的回应可用五个极短要点，非正式 schema：
- **观众/戏剧任务**：该选择要让观众看到/听到/理解或暂不知道什么；
- **来源与决定**：哪些作者硬约束与批准政策支撑它；具体镜头/表演如何实现；
- **一个真正不同的替代**：只有争点存在才列，比较收益与代价；
- **失败信号与证据状态**：明确错误、规划中有漏洞、物理/媒体待证分别说明；
- **局部修复指向**：改哪一层/哪一段，复检哪些相关范围；未实施修复不写“已解决”。

### 只设计、不执行的三组最小验证

| 样本 / 任务与干扰 | 通过判据 | 应否决的回答 |
| --- | --- | --- |
| **D K2/K5/K6**：从批准 Intent、B2/B3 Blocking 独立设计 Shot02/03；给一份旧 40mm 代理可读性不足的风险说明，再要求仅改 Shot02 | 不遗失“观众先见、林首轮未见、周仅推断、林二次见”；提出有观众证据任务的关系镜/客观插镜取舍；显露窗口、邻镜与状态检查；只改受影响范围，未证仍标未证 | 把周的 POV 拍成看见钥匙、只换 85mm 无理由、直接宣布像素可读或一改镜头就重写整场 |
| **C K2/K3/K5**：陈主动停句、许听懂、两次广播；比较同框和许的反应镜 | 保持自停→许听懂→原广播次序及自然表演政策；解释切镜如何改变观众归因，声音不是仅在后期处理 | 令广播打断陈、把许知情当未证事实、为风格创造额外情史/夸张动作 |

**检验知识是否真的被用上**：在未来实施样机时，同一冻结输入做最小对照：①仅阶段普通指令与 Scene Spine；②加问题触发专业小节。比较在未直接泄题的局部改动/相近反例中，是否**做出不同且有源约束支持的选择**，是否避免错误、说明取舍及停止无关加载。仅数专业术语、引用多少文档、写了几个镜头都不算成功。若两组差异只是术语丰富，应裁减该模块而非扩大文档。

**静态入门验收（实现后才执行）**：三例的确定性硬约束不能失败；专业取舍有真实观众任务和至少在存在争议处的合理替代；失败风险与验证状态不伪称媒体已证；局部重试必须留住整场 Intent 和交付责任；不相关专项不能无故加载。文本规划通过不表示 H3、真实几何、观众观看效果有效。

## 11. B-flex 细化｜阶段切换、正式检查点与上下文重建（2026-11-14；设计候选）

**用户审阅位置**：用户倾向“弹性混合调用”，已明确赞成 Shot Plan 上下文包、L0–L4 知识组织与最小文本验收。此处是按该方向进一步细化，**不将具体检查点/触发阈值误记为全部批准的实现规范**。仍遵守 WAR-74 的默认两处用户审阅 A/B；K1–K7 候选专业规则还未全量采纳。

### 11.1 四个维度分离

- **逻辑创作阶段**：Intent、Beat、Blocking、Shot（Review 横切）。阶段边界标识工作目标/输入产物/可修改范围，并不是模型会话边界。
- **模型执行会话**：一次模型调用可在当前阶段迭代，甚至连续探索多个尚未批准的阶段。一个阶段也可在多次调用/多种模型间恢复。阶段与调用没有一一对应关系。
- **存档检查点**：供恢复/比较的候选快照不等于用户批准。正式批准只以当前项目持久化决定为准；会话记录只是探索证据，不能隐式覆盖。
- **编排责任**：v0 只需简单调用端（人或最小程序）决定“继续/刷新/恢复”，加载相应阶段卡和知识，展示候选与审阅结果；不要求独立长期运行的 Orchestrator Agent、全自动流程图、并行专家会议。

### 11.2 三种常规调用模式（+ 可选独立 Review）

| 模式 | 适用条件 | 输入/动作 | 不能做什么 |
| --- | --- | --- | --- |
| **Continue 连续探索** | 同一场景、正式上游版本不变，现有上下文明确且能追踪当前候选 | 沿用模型会话；转阶段时更新工作目标与必要 Reference，保留尚有效的创作取舍 | 把聊天里未经批准的尝试升格为正式 Intent；仅因跨阶段就强制清空 |
| **Refresh 上下文刷新** | 当前会话变长或出现新问题，收到局部修改反馈，或部分上下文可能陈旧但仍可继续交流 | 从当前批准版+相关候选重投 Scene Spine、阶段包、差异和风险；显式声明旧结论哪些不再适用；仅补触发的专业章节 | 只说“沿用前文”，不核对原始批准约束和局部状态 |
| **Resume 独立恢复** | 新会话/换模型、从历史保存点重做、需要隔离受污染上下文、用户明确要求独立复核或恢复 | 选择明确的已批准版本与特定候选版本，重建 Scene Spine + Local Packet + 理由/未证；同一上下文包可交给不同模型 | 在不说明基线的情况下混合两个候选、把旧缓存当成当前正式版本 |

调用选择的**概念优先级**：
1. 若检测到源/已批准硬约束发生变化或冲突，先**阻止沿旧依据自动产出正式成果**，定位上游改动和影响范围；必要时回用户授权。这不是简单换成 Resume 就能解除的冲突。
2. 若丢失当前项目的权威依据、会话可信度不足、切换模型/会话或明确局部重试，选 Resume；批准版与被选候选都必须带版本定位。
3. 若仍在当前会话但出现反馈、上下文漂移风险、需要新专项知识或当前讨论范围扩大，选 Refresh。
4. 其他一般选择 Continue。**不规定固定 Token 数、轮次或阶段数阈值**；未来按实际测量再设提示/自动化条件。
5. 若存在高度争议的创作判断/风险或明显近失误，可单独调用短时专业 Review（可用另一模型）。Review 提交反例与影响定位，不成为默认强制双模型流程，不自动批准修改。

### 11.3 双检查点层级：候选保存 vs 正式批准（默认机制已确认）

| 事件 | 建议保存 | 权威状态 | 人工审核 |
| --- | --- | --- | --- |
| 一次内部迭代、同镜两个机位候选 | 临时探索即可；实质候选/理由可被会话记录 | 原批准版保持不动 | 不强制 |
| **逻辑阶段交接**（如 Beat→Blocking、Blocking→Shot） | **轻量候选快照**：阶段语义结果、重要依据与取舍、未解决问题、依赖的上游版本、局部变动范围 | 候选，供下一阶段或 Resume 使用；不视为已获准的事实 | 不增加新的默认用户审批 |
| **审阅 A**（Director Intent） | 确认后的 Intent、关键故事约束和政策理由、上游引用、用户选择 | 按 WAR-74 的正式批准状态持久化；B 的上游基线 | **用户默认审阅 #1** |
| Beat/Blocking/Shot 连续创作至计划 Review | 保存最新候选阶段产物与必要中间快照；保留尚待验证项 | 尚未批准的候选链，不能冒充 B 已批准 | 争议/硬冲突时才提前升级 |
| **审阅 B**（全场 Plan/Review） | Beat/Blocking/Shot 及横切 Review 的可追踪一致版本、残余风险/例外和已检范围 | 用户确认后成为新的批准基线；可有条件接受未证风险，但不得放行硬故事冲突 | **用户默认审阅 #2** |
| 批准之后局部修改 | 从批准版派生**候选修订**，显示目标、实际 diff 与被影响对象 | 原批准版本持续有效，直到修订完成审阅/应用 | 依 WAR-74 分级审阅，按风险/影响必要范围确认 |

注：这里的“候选快照”是调用/恢复的**语义要求**，并非强制新建 WAR-35/52 字段或数据库表；须复用现有 approved/candidate/Review/依赖语义，不得假设生产存储 API 已落地。阶段交接保存只含明确有用的决定，不保存模型隐藏推理或历史对话全文。

### 11.4 不让跨阶段反馈被卡死

**阶段切换可逆**。若 Shot 发现钥匙在现有 Blocking 下不可能对观众可信可辨，可以回 Blocking 比较演员位置、注意引导、道具暴露窗口等*候选改动*，再回到 Shot；但这些动作不能越界修改“观众先于林发现、周仅推断”的 Story Basis 事实。

**变更分为三类**：
1. **纯局部表达改动**（机位/构图/焦点/剪点）：同 Session Continue 或 Refresh，复核该 Shot、相关邻镜、局部认知窗口和全场任务覆盖；不强制重新批准 A。
2. **上游候选范围内的创作改动**（Blocking 身位/动作或 Beat 时间安排）：先提出关联候选修订、标注依赖的镜头与可能变化；当前会话可往返，但提交前须完成必要的下游复检与审批层判断。
3. **作者事实/已批准 Intent 硬约束变化**（例如周突然确实看见钥匙）：不是“局部镜头调整”，必须上行请求变更并获得相应批准，旧的依赖决定标**待复核/不可沿用**，不得静默更新正式事实。

**依赖波及最小规则**：从被编辑对象定位直接依赖→邻镜/声画接缝→受影响的观众第一次知情/叙事时序→全场 Beat 交付责任；只重建这些范围而保留全场 Scene Spine。若跨场景硬约束变化影响更多内容，则扩展审阅范围；不盲目全部重做，也不把局部通过冒充整场通过。

### 11.5 恢复包的最小结构（调用视图，非新 Schema）

一次 Resume/Refresh 的上下文按这个顺序临时组装：

1. **Authority**：场景与任务目标、Story Basis 权威引用/已确认禁项、当前已批准 Director Intent（含选择理由和整场政策）、各正式依据的版本定位。
2. **Scene Spine**：全场观众认知弧线、Beat 变化与交付责任的短摘要、不得丢失的相对时点/原话/关键行为。**不是只给 ID、hash 或“详见前文”**。
3. **Scope & Current Packet**：此调用工作阶段、目标 Beat/Blocking/Shot（含相邻状态和关键中间时刻）、当前有效候选及其与批准版的差异、已知的未证风险。
4. **Professional Knowledge**：L0 短原则、该阶段任务卡、针对真实问题的 DS/TF/VM 少量 Reference；保留来源定位与版本。以前已经判断的知识可提供简短适用结论，但争议时需回读原方法/原文。
5. **Expected Return**：当前要做的专业决定、与上游关系、候选取舍、发现的确定冲突和待媒体风险；正式提交要求留待已有数据/工程契约，不让 Agent 计算校验指纹。

**压缩准则**：优先缩减历史未采用方案、重复解释、无关镜头和工程校验日志；不可压掉作者硬约束、全场 Intent 的创作理由、会改变镜头选择的知情/声画时点、必要原文、最新用户反馈及状态。摘要无法保真时直接回读精确来源段落。

**来源冲突/缓存失效**：重新装配时先核对当前权威版本与工作候选所依赖的版本；不匹配即标需要重审或返回用户，不能把生成过的历史回答“自动补成新的批准版本”。文件的版本/依赖一致性交给 WAR-35/52 既有契约/未来工程实现；Agent 只收到语义差异与创作冲突。

### 11.6 D《错过的钥匙》的三段调用示意（设计例子，未实际调用）

**Continue**：审阅 A 批准“观众先见、周只是推断”的 Intent。当前导演会话连续推进 B2 首次露出、B3 再遮、Blocking 与 Shot02/03。发现关系镜中钥匙偏小后，直接比较变更构图/同镜注意引导与客观插镜；保留周并未目击的硬约束。Beat→Blocking→Shot 之间不强制启动新调用。

**Refresh**：用户指出“Shot02 看不到钥匙，先调整这个镜头”，会话仍能继续，但需要重新供给已批准 Scene Spine、B2/B3 关键时点、相关 Blocking、此前 WAR-72 代理像素不足的**证据边界**、Shot02/03 邻镜及当前候选；调用 K5 与必要 K6，比较收益/代价。不能把 27×9px 代理证据当真实成片定论。

**Resume**：几天后新会话或换模型继续修改 Shot02。仅用批准快照 + 精确指向的 B2/B3 + 有关 Blocking/邻镜 + 用户修改目标 + 风险/理由组成包；不装载旧全会话。若某候选反打暗示周已看到钥匙，返回故事冲突，不能以“已通过局部镜头优化”放行。

### 11.7 v0 最小职责与不实施事项

- **Director Skill**：持续创作、专业知识路由、解释摄影/调度取舍、指出上游依赖和创作矛盾；不拥有批准状态写入的最终权力。
- **简单调用端（可以先由人工调用）**：选 Continue/Refresh/Resume、准备当前正式输入与候选、呈现差异和人类审核关口；无需独立“Director Orchestrator Agent”或自动 DAG 调度系统。
- **WAR-35/52 对接的未来工程层**：负责数据规范/引用版本/批准状态与确定性依赖校验；本轮仅定义**需求边界**，不宣布已经存在生产 API/Engine。
- **用户 A/B 审阅及必要例外审批**：保留 WAR-74 两处默认；无关的小迭代不额外审批；确定性硬冲突不能以“接受未证媒体风险”来通过。
- **未来 Canvas/媒体审阅**：只负责呈现与后续实证，并记录编辑反馈；本轮不启动。

### 11.8 最小对照验收补充（仅设计，不运行）

1. **连续性**：同会话跨 Intent→Beat→Blocking→Shot，不丢全场观众信息主线；Shot 返回 Blocking 修改后仍守 Story Basis 与已批准 Intent。
2. **恢复等价性**：给新会话/不同模型仅恢复包，能独立指出 D 的三方不同知情时点、镜头取舍与未证风险，而不依赖原完整聊天。目标是**关键不变量/决定理由一致**，不要求生成文本和镜头数相同。
3. **候选隔离**：同会话产生多候选，不应因此改变批准版；被拒候选不应在下次恢复时成为事实。
4. **局部最小复检**：只改 Shot02 时不强制重新设计全场，却检查 Shot03、关键线索第一显露的观众窗口和整场覆盖；用户要求改变周认知必须上行。
5. **加载效率**：没有复杂遮挡/声音/背字时，不加载全部 DS/TF/VM；真实触发时能正确选 K2/K5/K6，选择结果不只是摄影术语堆积。

**用户确认的 v0 默认机制（2026-11-14）**：在**有意义的逻辑阶段交接**时自动保存可恢复的轻量**候选快照**；审阅 **A（Director Intent）/B（整场 Plan 与横切 Review）**保留为两处**默认用户批准关口**；额外专业审阅仅在风险、重大分歧或确定性冲突需要时触发，不新增每阶段常规人工审批。微小内部推敲不强制逐轮持久化，阶段候选快照不得默认为已批准事实。该原则属于**已采纳的设计决定**，不表示自动保存技术接口已经实现。后续细化保存粒度（何种交接/往返需要新快照）、版本归属与正式提交接口，但不能反向改变这项默认原则。

**下一停点**：沿已经确认的候选/批准两类检查点，收窄到最小 Stage 调用契约与 Continue/Refresh/Resume 切换边界，再讨论正式 Skill 文件组织。具体自动切换阈值、模型路由、持久化接口需结合样机和 WAR-35/52 现有语义验证，不在本任务虚构已运行的 Engine。项目工作树还有其他任务在途修改；不混合提交、不推送。


## 12. B-flex 最小调用契约 v0（2026-11-14；用户已确认作为后续 Skill 设计基线）

**依据与边界**：承接 §9–11 已确认的知识/Shot Plan 上下文/最小验收，以及“有意义的阶段交接自动保存轻量候选；A/B 两处默认用户批准；额外审阅按风险触发”。本节仅明确**阶段调用所需语义、快照保存粒度、模式选择和调用端职责**。不是新的 DirectorPlan Schema、审核类型、运行时 API 或已实现的 Engine。

### 12.1 工作单元：阶段、会话、状态彼此独立

- **Stage** = 本轮专业工作目标和影响范围：Intent / Beat / Blocking / Shot Plan；Review 横切，不是新增串行的生产阶段。
- **Session** = 可延续的模型工作上下文；一个 Session 可跨多个 Stage，一项 Stage 也可跨多个 Session 与模型继续。
- **Candidate** = 可恢复的阶段创作候选，保留所依赖的批准基线、实质决定、关键取舍及未证风险；**保存候选不表示批准**。
- **Approved** = 必须通过 WAR-35/52 现有方向的正式 Review/Decision 与有效来源绑定的状态；当前 WAR-35 RC 仍处冻结复核，不假设已有可调用生产 API。

### 12.2 最小 Stage Call 输入包（字段族示意，非 JSON Schema）

| 信息 | 最小充分内容 | 提供责任 |
| --- | --- | --- |
| 任务范围 | 本次要解决的专业问题、允许修改的 Stage/Beat/Shot、不得改动的内容 | 用户意图＋调用端 |
| 运行模式 | Continue/Refresh/Resume、目标 Stage、是否允许返回上游提出修订 | 调用端 |
| Authority | Story Basis 权威来源、当前适用的批准 Intent/全场政策、版本定位、硬约束和来源可信状态 | 正式项目记录＋调用端 |
| Working candidate | **选定一个**活跃候选分支、其依赖的批准版、实际差异；没有候选时明确标无 | 候选存档＋调用端 |
| Scene/Stage Packet | Scene Spine、有关 Beat/Blocking、关键中间时点、镜头与邻镜、必要原文及原始状态 | 调用端按需组装 |
| 专业知识 | 短 L0 原则、当期 Stage 卡、真正问题触发的 DS/TF/VM 小节和来源版本 | 调用端提供索引，Skill 做专业适用判断 |
| Review 背景 | 最新用户意见、有效风险与证据等级、被否决候选**影响本轮的原因** | 项目记录＋调用端 |

Continue 可在现有已核对上下文上仅提交变化项；Refresh 在原会话重投权威依据、活动候选、差异与必要知识；Resume 从**批准基线＋选定候选**重新构建所需的全部包，不能只传 ID、hash 或“详见之前”。关键来源解析失败时不得伪造事实或生成可提交的正式成果。

### 12.3 最小 Stage Result：专业反馈，而非审批对象

一轮输出至少可表达：

1. **Proposal**：本次实际提出了什么导演选择、覆盖什么对象与观众信息任务；可以选择保持原方案。
2. **Reason/Alternative**：真正影响选择的来源、专业取舍及相关替代；不机械罗列全部镜头术语。
3. **Scope/Impact**：请求修改范围与实际建议变化，涉及的上游层、依赖后继、邻镜、知情与时间窗口。
4. **Risk/Evidence**：确定性硬冲突、规划假设、媒体/观众未证分开记录；建议修复不能伪称已修复。
5. **Next action**：建议形成候选交接、返回上游修订、请求用户变更授权、触发独立风险审阅、或因输入不足暂停。

以上是对外的专业语义，不新建审批状态枚举；模型不返回隐藏推理、JCS 指纹或自签批准。候选存档与正式审阅由调用端及工程层办理。

### 12.4 候选快照保存粒度：默认“有实质成果的交接”

| 事件 | 建议动作 | 需要避免的错误 |
| --- | --- | --- |
| Beat→Blocking、Blocking→Shot 等实质阶段交接 | **自动保存**上一阶段可用的候选语义、版本依据、理由、范围和未证项 | 不把完成交接当已正式批准 |
| Shot 退回 Blocking 调整行为，再转回 Shot | 保存**新的** Blocking 候选，标记受影响 Shot 需复检 | 不无痕覆盖旧分支/自动合并相互冲突的备选 |
| 用户明确暂停、准备新会话或换模型，当前有未保存的重要进展 | 优先保存轻量候选；尚无可用结果时只记录 WIP/停止位置 | 不虚构“阶段已完成”；意外中断仍可能丢失最后几轮未保存探索 |
| 文字润色、讨论机位但未作可交接决定、无实质差异 | 不自动存每轮，不创建空快照 | 避免巨量候选版本 |
| A/B 用户批准 | 调用**正式** Review/Decision 和版本机制保存批准 | Candidate 落盘不得升级为 Approved |
| 批准后局部修改 | 从批准版派生可追踪的修订候选，明确目标和实际 diff | 不直接覆盖旧批准快照 |
| 存在并行备选候选 | 明确当前活跃的一个分支，其他仅按需查看 | 不把多个历史候选混成一份“当前事实” |

候选快照语义下限：**目标 Stage/范围、来源与批准基线定位、当前可用决定、关键理由或拒绝方案理由、变更与受影响对象、未证项、下一步**。这是需求，不要求额外建立七个数据库字段；存储/版本映射应复用 WAR-35/52 方向的公共语义。

### 12.5 Continue / Refresh / Resume 的选择顺序

1. **先检查 Authority 有效性**：正式来源、批准状态或依赖版本不一致，或者用户所需修改违背故事硬约束时，阻止从旧依据直接交付当前有效成果；明确需要重审/上行授权。简单切换 Resume 不能自动解除冲突。
2. **Resume**：跨会话/跨模型接手、要求独立重新审阅、历史会话可信度不足、混入被否决候选，或需要从明确版本重试。从批准基线和**一个明确的工作候选**重新装包；旧聊天不作为唯一来源。
3. **Refresh**：会话仍可信但收到实质用户反馈、任务范围变化、阶段依赖有更新、语义压缩风险或新的知识主题。原会话重投正式 Scene Spine、候选差异、目标阶段与必要来源；发现污染不能修复时升级 Resume。
4. **Continue**：版本匹配、当前候选可定位、信息足够且无需隔离；允许在同一模型会话跨 Stage 探索及返回上游做候选修订。
5. **条件独立 Review**：重大专业争议、近似硬冲突、未证风险影响关键镜头等触发短时独立核查；不自动拥有 A/B 用户批准权。

v0 **不固定 token、轮次、阶段数、每次阶段切换必开新 Session、每阶段必用第二模型**的阈值。模式选择理由可以写为简短执行记录，不需要塞进导演专业推理包。

### 12.6 版本、冲突与局部回退保护

- 每次模型结果都必须能对应本次输入的**权威基线、活动候选和工作范围**。模型运行期间若权威源版本改变，旧结果最多保留为隔离草案；不得基于陈旧依赖直接提交为当前候选或据此通过审阅。
- 一个 Shot 修改若暗含人物知情/故事因果变化，应提示返回 Beat/Intent/Story Basis 修改并等待必要授权；不能把越界编辑包装为局部摄影变化。
- 改 Blocking 时，后续 Shot 的旧结果不应直接继承已通过状态；至少复核受影响的邻镜、知情窗口与整场任务覆盖。
- 审阅 A 是 Intent 的正式关口，**不是整场计划批准**。审阅 B 才是全场计划的默认批准关口。旧 Check/Decision 的继承必须由 WAR-35 的精确版本/依赖规则和相应真实实现校验，本方案不另造继承算法。
- 未证媒体风险不能通过换模型、改会话或压缩上下文自动变成通过；真正的媒体验证在后续 Canvas/H3 阶段。

### 12.7 D《错过的钥匙》的调用追踪（纸面例子，未运行）

| 场景 | 模式 / 专业输入 | 保存 / 复检 |
| --- | --- | --- |

### 12.8 最小职责分工及验收

- **轻量调用端（v0 可先人工/脚本）**：选择 Stage/mode 和一个候选、准备 Authority 与 Stage 包、记录目标变更、触发候选保存及用户审批入口。
- **Director Skill**：选择专业方法、作出可解释的导演取舍、提出具体候选与跨层返回建议、标记风险；不能写正式审批或重算依赖签名。
- **工程契约适配（后续）**：利用 WAR-35/52 的版本/Review/Check 语义实现持久化与一致性检查；不凭字段完整就认定专业表达有效。
- **用户**：默认审阅 A/B 及因硬冲突/高风险升级的必要决策；风险独立 Reviewer 不替代用户。

未来最小文本样机检查：阶段交接能被新会话恢复；Shot→Blocking→Shot 只复检相关范围；被拒候选不污染 Resume；权威版本冲突阻止错误提交；空转不产生检查点；独立 Review 无法自行把 Candidate 升为 Approved。**尚未实际执行上述案例。**
