## 2. 最终认识：三个 Skill 的职责差异

| 必须解决的问题 | 代表性贡献 | 观察到的边界 | 对自研的含义 |
| --- | --- | --- | --- |
| **剧本怎样被观众理解** | Toonflow：脚本事实→逐场情绪/表演与观众信息关注→Storyboard；WAR-73 单一关注点曾使许的无对白反应镜从2秒变4秒 | 单次同条件输出不能排除随机性；多处镜头和总时长也变化（A30.5s→B33s） | 明确观众应知道/尚不知道/应注意谁，不把“改关注点”当成只影响一个 Shot 的承诺 |
| **表演、调度与镜头如何相互约束** | DirectorSKILL：Script/Subtext→Beat→Director’s Book→Blocking→Shot Plan；D 中钥匙与人物知情状态、E 照片可读时点被文本追踪 | C Beat/Shot 越界需修订；D Shot04 超Book限长、Shot07→08切镜问题、Shot08 Red 交接未闭环 | 分离剧本事实、导演政策、暂定预算、动作/状态与分镜候选；建议修正之后必须回写并跨层复核 |
| **已决定的镜头怎样准备图像/参考** | ViMax：镜内FF/Motion/LF及跨机位的 Camera Tree 参考依赖 | Camera Tree不是叙事状态账本/真实视线几何；单镜提示可能自行加戏或重复动作 | 仅在真正需要独立首帧/关键帧和多机位图像资产时采用，不作为当前 H3 Ref2VA 三实体图多Beat提示词的强制阶段 |

**整体结论：**三者各有正向机制，但无证据支持“整套串联必然更好”“一个 Skill 可替代其余所有职责”或“镜数越多越有导演水平”。需要按问题借鉴规则，而不是合并源项目的全部 Agent/画布流程。

## 3. 跨任务暴露的五个实际断点

1. **故事表达与镜头之间缺少可追溯的“为什么”**：原剧本意图与模型推断必须区分；每个 Beat/Shot 的画面信息、观众知情和情绪任务要能回指上游。WAR-73 展示单一“关注许”指示可对应反应镜延长，但不证明稳定复现。
2. **阶段输出不是自然闭环**：WAR-70 的 C B1/B2 人工合并使原5 Beat变4，后续 Shot 仍7且仍需检查边界；D Book 最大6秒与 Shot04 7秒未协调，Shot07/08 近似同机位切镜未实际修复。**发现/建议/修订/复检/确认**是不同状态。
3. **文本状态链≠物理可执行**：D 钥匙 K 文件遮→露→再遮→再次露→交付，E 照片文字可读时点可在文本追踪；WAR-72 Blender 发现表演身体与桌面碰撞、Shot02 40mm MS 中K约27×9px且部分遮挡。源 Book 曾要求K可读、可选85mm，但最终Shot02缺实构图验证。剧情逻辑成立不保证观众看得清。
4. **单点改动会影响其他规划**：WAR-73 固定输入仅改一行，A/B均11镜和7句对白完整，但许反应从2→4秒同时全片30.5→33秒、片段边界/其他景别变化。需要“预期影响范围—实际差异—超出范围的修改”的审阅和保留/撤回决策。
5. **风险评分和实测效果是不同证据层**：D Shot08 物理互动Red覆盖触发有据，但候选拆分08a仍Red；C/D/E/ViMax样本跨模型与形式有混杂；无视频/真实观众理解的统计证明。不能把六维Red/Amber当H3成功率，也不能把一次文本符合导演想法当成最终成片有效。

## 4. 自研 Director Skill v0 的候选设计原则（非实现规格）

| 候选原则 | 最小要保证的能力 | 证据来源及约束 |
| --- | --- | --- |
| **唯一权威的事实/意图/决定** | 区分已确认剧本事实、用户导演关注/约束、模型建议、未知；修改必须可追溯且不擅自升级为事实 | WAR-69/70、WAR-73 |
| **先问观众需要理解什么** | 对关键Beat标明观众何时看见/明白/尚不应得知什么，角色谁知道什么；解释镜头选择依据 | WAR-61/65、D/E、WAR-73 |
| **表演/Blocking/Shot 的薄契约** | Beat state-in/out、人物与道具状态、可见动作及眼线；每镜信息任务、景别/时长/切点和来源 | WAR-65、WAR-71、WAR-72 |
| **可计算检查 + 未证项** | Beat/Shot 时段、台词不删改、道具状态、预算冲突及原计划偏差可机检；镜头几何或观众知觉未测时必须标未知 | WAR-70/71/72 |
| **局部反馈影响传播审阅** | A/B按事件对齐，报告预期更改、实际连带修改、需用户确认的取舍，不自动接受整片新计划 | WAR-73 |
| **风险处理不能停在标红** | 明确风险发现、候选策略、实际修订、复检和用户接受/保留未证；不为求绿色擅自降分 | WAR-65/71 |
| **渐进式媒体能力** | 当前以三实体参考图+多Beat Prompt为目标；关键帧/FF/Motion/LF/Camera Tree、Blender/图像审阅按真实需求再接入 | WAR-66、WAR-72；不是强制产品阶段 |

“阶段”只是候选职责边界，**不要求七个独立 Agent、不规定按这七行创建节点或文件、不直接继承三个原 Skill 的庞大工作流**。最小原型应优先把一次用户导演意图调整传至 Shot Plan、解释连带变化并提示未证风险。

## 5. 已有证据的“保留／简化／暂缓”

- **保留**：故事事实与导演意图区分、Beat state-in/out、人物知情与道具状态链、观众信息任务、镜头用途与表演注意事项、时间/场次核查、风险分类与人工审阅、修订后复检。
- **简化**：Director’s Book 镜数和长短预算当可解释/可批准的规划约束；剧本→导演→分镜不需要复制多个 Skill 的全套表；不为每个中间产物增加冗余文档或固定Agent角色。
- **暂缓**：完整 Toonflow App canvas workflow复现，ViMax Camera Tree图像链、自动观看理解/VLM评分、复杂Blender物理演算与H3生成集成；待实际 Canvas 交互审阅阶段决定何时值得做。
- **不采纳的无证推断**：三方法性能排序、自动组合优于单Skill、Red必失败、几何文本通过代表镜头能看清、改变单行意图必然只更改目标镜头、自动检查代替人工导演审阅。

## 6. 设计启动关口：什么已足够，什么必须另行决定

**足够进入自研 Director Skill v0 的概念设计**：三种原Skill的定位和互补边界、三个不同剧本（C/D/E）的正反例、DirectorSKILL交互+几何反例、Toonflow单点意图文本响应及其修改传播风险、ViMax 镜内描述/视觉参考边界。继续反复跑相同脚本对“如何设计v0”价值有限。

**设计新任务的第一批决策，尚未批准**：
1. 选一条最小端到端“已确认剧本与约束→观众信息/情绪意图→Beat/Blocking→Shot Plan→检查与用户批准”的闭环；不先规定Agent数量、产品UI或组件。
2. 决定哪些信息需要用户明确确认、哪些由模型暂拟、哪些属于只读验证；“阶段通过”的最低口径是什么，以及不通过如何退回受影响的上游。
3. 明确一次导演反馈如何在小范围修改和全局一致性之间取舍：先展示修改差异、受影响镜头和时长，再由用户选保留或撤销。
4. 把 H3 Ref2VA（实体图参考、1–3 Beat / 5–8s）作为第一版真实输出约束；不要将独立Storyboard图、Add Guide或多镜逐帧资产强加为当前前置条件。
5. 指定文档与版本规则：Linear Issue仅导航/决定；Eric `docs/` 下独立 Markdown为详细唯一权威，输入及模型结果、规则版本、SHA按需冻结；未经批准不修改原版 Skill。

**暂不构成设计阻塞**：真实观众盲测、Shot02 K 的最终可读修复、D Shot08 交接完成视频、E文字在成片的可读性、ViMax全图像链或真实 Canvas 画布自动审阅；这些是在集成和制作阶段再定义验收，不可伪称已完成。
